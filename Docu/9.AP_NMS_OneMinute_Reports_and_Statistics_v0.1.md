# AP and NMS One-Minute Reports: Contract, Calculations, and Acceptance Goals

**Version:** 0.1 — review draft  
**Date:** 2026-11-13  
**Purpose:** Agree on the data we intend to collect and the statistics we intend to calculate, then use this document as the checklist for validating the implementation.  
**Scope:** New access-point firmware, Internet iperf3 sessions, NMS relay, web-backend interpretation, and DataLake preservation.

This is a working specification, not a declaration that every field has been independently validated. After review, revise it in place as tests establish actual behavior. Do not silently change an assumption into a measurement.

## 1. Goal and present position

Our intended output is, for each reporting interval, the **average number of wireless transmissions per minute** and the **average duration of those transmissions**, separated by:

- User/robot on the fronthaul.
- Traffic category: VO, VI, BE, or BK, as assigned by the gateway classifier.
- Wireless link and channel.
- Transmission and reception direction.
- Fronthaul versus backhaul. The whole backhaul can be one `BACKHAUL` category; user/category attribution within the backhaul is not required initially.

A wireless transmission can carry several aggregated packets. In this document, the physical transmission unit is the **physical-layer protocol data unit (PPDU)**. We must not silently use packets, the old `frame_count`, or complete transmission-and-response exchanges as interchangeable units.

The initial model accepts rough estimates, with low retries and collisions as the intended operating region. That assumption does not establish that an individual test actually had low retries; available radio counters should be inspected.

## 2. Terminology and direction conventions

| Term | Meaning here |
| --- | --- |
| Access point (AP) | Controller or agent wireless device |
| Network management system (NMS) | Receives, queues, identifies and forwards reports; it does not interpret wireless statistics |
| Fronthaul | Wireless link between a robot/station and its serving AP |
| Backhaul | Wireless link between APs in the mesh |
| Packet / MSDU | Driver-reported data-packet unit, called a MAC service data unit. Joanna reports it matches interface packet counts closely; this is a firmware/driver interpretation, not a universal statement that every IP packet always equals one wireless frame |
| MPDU | MAC protocol data unit; a wireless MAC frame unit used by the radio retry counters |
| PPDU | Physical-layer protocol data unit; one physical wireless transmission, possibly carrying aggregated data |
| Frame exchange sequence (FES) | Physical transmission plus its immediate response exchange, including the gap before acknowledgement. Per-peer TX airtime uses this meaning |
| TX / RX | Transmit / receive, always from the reporting AP's viewpoint |
| AC/category | In the current report, a gateway application-classifier category mapped to VO/VI/BE/BK; **not a measured wireless access category** |
| MCS | Modulation and coding scheme; counts in these reports are radio-level PPDU statistics |
| BW / NSS / GI | Channel bandwidth / number of spatial streams / guard interval |
| Delta | Increase in a cumulative device counter between two reads; reports carry interval deltas rather than cumulative totals |

For a robot served by AP6 behind controller AP1:

| Traffic | Robot–AP6 observation | AP6–AP1 observations |
| --- | --- | --- |
| Download to robot | AP6 `ap_tx`, station peer | AP1 `ap_tx` to AP6; AP6 `ap_rx` from AP1 |
| Upload from robot | AP6 `ap_rx`, station peer | AP6 `ap_tx` to AP1; AP1 `ap_rx` from AP6 |

The two observations of the same backhaul transmission are **not two separate link transmissions**. Preserve both for validation, but choose one canonical observation when calculating a link total. The fronthaul transmission and the forwarded backhaul transmission are separate transmissions, even when they carry the same application data.

## 3. What changed from the previous design

| Aspect | Earlier design/report | New design/report |
| --- | --- | --- |
| iperf3 endpoints | NMS client, robots passive servers; local-network traffic often invisible to gateway byte accounting | Robot client initiates outbound connection to Internet server; data crosses controller's Internet gateway |
| AP report layout | Top-level flat `records` with `sta_mac`, `ac`, `frame_count`, `avg_frame_duration_us`, download/upload bytes and MCS information | `format_version: 2`, separate `radios`, and nested `peers[].records` |
| Wireless direction | Old station frame statistic concerned AP TX | Explicit `ap_tx` and `ap_rx` |
| Byte source | Gateway accounting; agent could repeat controller counters while holding a stale association | Measured local peer `ALL` byte/packet counts, alongside separately sourced gateway category bytes |
| Byte scale | Unnecessary division by eight existed | New sample byte magnitudes are consistent with byte units; do not apply another factor of eight except converting bytes to bits |
| Transmission counts | Old `frame_count` mixed estimates and ambiguous semantics | Packets and physical-transmission attempts are distinct; peer transmission counts explicitly estimated |
| Duration | Old computed/fallback value, often 48.8 microseconds | Measured TX duration sum, measured TX/RX histograms, and measured peer TX exchange airtime, kept separate |
| MCS scope | Some old labels suggested station-specific information | Radio scope explicitly stated; no independently measured per-peer MCS distribution |
| Backhaul | No explicit peer traffic record | Backhaul peer records at both ends, both directions |
| Unknown values | Could be confused with zero/defaults | `null` with unknown/unavailable provenance must survive |
| Upload packaging | Common small batch budget | AP reports sent separately from scan/iperf3 batches; several batches may arrive in one cycle |

Old-format compatibility is retained during rollout. That does not make the old and new statistical fields semantically interchangeable.

## 4. Ownership and data flow

1. **AP firmware/agent:** collect counters, form deltas, attach sampling windows and provenance, and compute explicitly labelled estimates.
2. **NMS:** validate the transport shape and timestamps, retain complete AP-owned data, queue it, add scanner/site identity, and forward it without inventing statistics.
3. **Web backend:** preserve raw data, resolve peer identities from status evidence, calculate version-aware summaries and derived statistics.
4. **History/DataLake:** retain complete measurements and supporting status/topology so analysis can be reproduced later.
5. **LIVE:** present a view of stored data. A stale panel does not establish that reports stopped arriving, and a current panel does not prove permanent archiving.

AP code changes belong to Joanna. Maintain a consolidated issue list for her rather than issuing separate firmware changes for every observation.

## 5. Expected AP one-minute report

### 5.1 Top-level structure

The following shows structure only; omitted arrays are not a complete test report.

```json
{
  "format_version": 2,
  "reporting_ap": {"mac": "<AP identity MAC>", "role": "controller or agent"},
  "device_name": "AP1",
  "time_start": "2026-11-13-13:23:22",
  "time_end": "2026-11-13-13:24:22",
  "interval_s": 60.2,
  "sampling_windows_s": {
    "peers": 60.195,
    "channel_time": 60.191,
    "gateway": 60.234
  },
  "units": {
    "bytes": "bytes", "packets": "MSDU", "ppdus": "PPDU",
    "durations": "us", "channel_time": "ms", "gi": "us"
  },
  "radios": [],
  "peers": []
}
```

| Field | Expected meaning/check |
| --- | --- |
| `format_version` | Explicit version 2; receiver also accepts the old format |
| `reporting_ap` | Device identity and controller/agent role; identity MAC is not necessarily a backhaul radio MAC |
| `device_name` | Human-readable AP name; retain NMS scanner/alias identity separately |
| `time_start`, `time_end` | Local interval boundaries using `%Y-%m-%d-%H:%M:%S`; whole-second precision |
| `interval_s` | Overall interval indicator; do not use it instead of a counter group's more specific window |
| `sampling_windows_s.peers` | Elapsed interval for local peer packet/byte/exchange-airtime counters |
| `sampling_windows_s.gateway` | Elapsed interval for classified gateway byte counters |
| `sampling_windows_s.channel_time` | Elapsed interval for channel survey counters |
| `radios[].sampling_window_s.host` | Host elapsed time between reads of that radio's firmware counters |
| `radios[].sampling_window_s.firmware` | Radio firmware's own elapsed interval; use for radio transmission/MCS/duration counts |
| `units` | Explicit units; no silent conversion or default scaling |

Different groups are read sequentially. Their elapsed durations and boundaries are not identical. The present report supplies elapsed windows, not separate absolute start/end timestamps for every group. Cross-counter alignment remains approximate at minute resolution.

### 5.2 Field-value objects and missing values

Many values are objects, for example:

```json
{
  "packets": {"value": 31454, "type": "measured", "source": "iw station dump tx packets"},
  "ppdus": {"value": 18080, "type": "estimated", "source": "radio TX data PPDUs tried x peer packet share"},
  "fes_airtime_us": {"value": null, "type": "unavailable"}
}
```

- `value: 0` means a valid zero only when the source supports that interpretation.
- `value: null` is not zero. Retain its `type`, `source`, `note`, and any assumptions.
- Missing fields are distinct from both zero and explicit unavailability.
- Empty distributions can be valid when only excluded legacy-rate traffic occurred. Do not infer from an empty MCS distribution that the radio transmitted nothing.
- Preserve unknown future additions in raw data.

### 5.3 Per-radio fields

Each radio needs identity, band, channel, center frequency, configured channel width, sampling window and reset information.

| Field/group | Meaning and intended use |
| --- | --- |
| `channel_time_ms.active/busy/tx/rx` | Measured channel survey deltas, in milliseconds; coverage is a radio/channel measurement, not a per-user category measurement |
| `tx.ppdus_tried_data` | Data physical-transmission attempts, including retries and broadcast/multicast traffic; excludes management according to report metadata |
| `tx.ppdus_tried_total` | Total physical-transmission attempts, including retries and management |
| `tx.mpdus_ack_failed` | Radio count of MAC-frame acknowledgement failures; not a per-peer retry count or collision count |
| `tx.mpdus_retry_limit` | Radio count of MAC frames reaching the retry limit; not interchangeable with acknowledgement failures |
| `tx/rx.mcs_distribution.values` | Radio-level physical-transmission counts by MCS; excludes legacy rates; exact population compatibility with other counters must be verified |
| `bw_distribution_mhz`, `nss_distribution`, `gi_distribution_us` | Separate marginal distributions, not a joint histogram of MCS/BW/NSS/GI combinations |
| `tx/rx.ppdu_duration_hist_us` | Duration histogram with 250-microsecond bins, excluding legacy-rate transmissions as labelled |
| `tx/rx.ppdu_duration_avg_us` | Estimated mean from histogram bin representatives, not an exact measured mean |
| `tx.ppdu_duration_sum_us` | Measured total TX physical-transmission duration, with success/fail components; Joanna's measurements indicate preamble included and response exchange excluded |
| `tx.ppdu_duration_avg_from_sum_us` | Duration sum divided by total attempts; all-attempt population, including management/legacy; separate reads can introduce small differences |
| `peer_packets_total.tx/rx` | Sum of local peer data packets on that radio, including backhaul peers |
| `effective_allocation_ratio.tx/rx` | Packet count divided by the chosen radio transmission count; an allocation ratio, not directly measured physical aggregation size |
| `counter_reset` | Interval affected by counter discontinuity; derived rates/statistics require invalidation or explicit handling |

The channel-survey object can instead be:

```json
{"value": null, "type": "unavailable", "note": "..."}
```

This occurs on AP6's radio carrying both a backhaul station interface and a fronthaul AP interface. It must not become an idle channel or zero utilization. Other radio counters remain usable according to their own validity.

**RX coverage caution:** the bandwidth distribution explicitly includes received transmissions such as neighboring-network beacons, unlike the MCS distribution. Whether the selected RX count/duration population contains unrelated non-legacy traffic still needs confirmation. Never force all distribution totals to be equal.

### 5.4 Per-peer structure and records

| Peer field | Meaning |
| --- | --- |
| `peer_mac` | Remote wireless interface MAC for this link; robot data-interface MAC or neighboring AP radio MAC |
| `peer_type` | `station` or `backhaul_ap`; unidentified types must not silently become stations |
| `peer_ap` | May be null in raw reports; backend can enrich summaries using independent status evidence |
| `radio`, `freq_mhz`, `interface`, `link_id` | Local link identity; retain them to distinguish interfaces/links rather than grouping solely by robot MAC |
| `counter_reset` | Peer-level discontinuity flag |
| `records` | Direction/category counters plus possible coverage-only metadata entries |

Expected record populations:

| Peer type | Record | Meaning |
| --- | --- | --- |
| Station | `ap_tx`, `ALL` | All measured local AP-to-station data packets/bytes |
| Station | `ap_rx`, `ALL` | All measured local station-to-AP data packets/bytes |
| Station | `ap_tx`, VO/VI/BE/BK | Classified download bytes; estimated packet/transmission allocation |
| Station | `ap_rx`, VO/VI/BE/BK | Classified upload bytes; estimated packet/transmission allocation |
| Station | Direction plus `category_coverage` | Classification assumptions/unknown coverage; may have **no `category` field** |
| Backhaul | `ap_tx`, `BACKHAUL` | Local AP sends to the neighboring AP |
| Backhaul | `ap_rx`, `BACKHAUL` | Local AP receives from the neighboring AP |

**Never add `ALL` to its category breakdown.** Never add a radio total to its allocated peer counts. Do not add fronthaul and backhaul bytes to produce unique application-delivered bytes; these are different link observations of forwarded traffic.

### 5.5 Peer counter meanings

| Counter | Source/status | Important qualification |
| --- | --- | --- |
| `ALL.packets` | Measured local driver data-packet delta | Retries excluded; not transmission count |
| `ALL.bytes`, AP TX | Measured local driver bytes | Joanna describes Ethernet frame lengths |
| `ALL.bytes`, AP RX | Measured local driver bytes | Includes wireless-header coverage; differs from TX by roughly 20 bytes/packet in her tests, not a guaranteed correction for all traffic |
| Category `bytes` | Measured gateway classifier counter | Different observation point/header coverage; can omit bridged local traffic |
| Category `packets` | Estimated from directional classified-byte shares | May allocate classified proportions to all peer packets; coverage assumption must stay visible |
| Peer/category `ppdus` | Estimated allocation of radio transmission counts | Common effective aggregation across peers/categories assumed; may exceed packets because of retries/broadcast allocation |
| TX `fes_airtime_us` | Measured peer frame-exchange airtime | Includes acknowledgements and management; may attribute the same multi-user exchange duration to multiple peers |
| RX `fes_airtime_us` | Unavailable | Do not synthesize a measured RX value |

nDPI application classification supplies the category labels. Generic iperf3 UDP currently maps to BK. Requested iperf3 traffic priority does not establish actual wireless category. This distinction is acceptable for the initial application-category model.

### 5.6 Coverage and quiet traffic

Gateway categories cover routed Internet traffic and the AP-local traffic covered by that implementation. They do not cover all bridged local-network traffic. Therefore:

- A measured peer `ALL` total must exist independently of gateway classification.
- If all packet counts are allocated using gateway category shares, the categories necessarily sum to the allocated total. That does not prove complete coverage.
- Unknown uncovered traffic remains unknown. Do not calculate a supposedly measured `UNCLASSIFIED` residual by subtracting differently defined gateway and driver byte counters.
- Retain valid zero-load intervals, coverage notes and unavailable counters.
- At very light load, a peer may be allocated many broadcast transmission attempts despite exchanging few packets. Such estimates require a quality warning, not reinterpretation as observed peer transmissions.

## 6. Supporting ten-second AP status

The one-minute report is not sufficient to resolve all identities and associations. Preserve the supporting status fields:

| Field | Use |
| --- | --- |
| AP scanner/alias/identity MAC | Stable AP identity |
| Fronthaul interface BSSIDs, band, channel, frequency | Resolve which AP serves a robot's reported association |
| Station association list and status timestamps | Supporting association evidence; can become stale after roaming |
| `backhaul_mac` | Current upstream backhaul network BSSID; empty on controller or disconnected agent |
| `wireless_macs.backhaul_sta[band]` | This AP's station-interface MAC; visible as the peer at the upstream AP |
| `wireless_macs.backhaul_bss[band]` | This AP's backhaul network BSSID; visible as the peer at downstream agents |

Backend backhaul mapping must use one unique fresh same-site match. Current code uses a 180-second freshness bound relative to the report end. Unresolved/ambiguous/long-delayed reports keep `peer_ap` unknown. Preserve raw reports unchanged; put enriched identities and their source in summaries.

An AP1 `ap_tx` record toward AP6's station-interface MAC corresponds to AP6 `ap_rx` from AP1's backhaul network BSSID. These MACs need not be equal to either AP's registration identity MAC.

### 7.3 Cadence and batching

- NMS runs a nominal 60-second bulk-upload cycle. The loop waits after processing, so this is not a guarantee of exact wall-clock minute alignment.
- APs independently produce nominal one-minute reports with their own phases and sampling windows.
- Step 3 sends AP reports individually, apart from scan/iperf3 batches. Several HTTP uploads and several history measurements can therefore arrive during one cycle or within the same second.
- Do not expect one single batch per minute containing every AP and the current iperf3 session.
- Scan/iperf3 POST limit remains 100,000 bytes. AP POST limit is configurable and currently 2,000,000 bytes, including the serialized envelope.
- Current AP uploader permits up to 12 POST attempts per cycle and rotates the starting scanner. Oversized/failed entries are retained with diagnostics; read windows and Redis stream retention are bounded, so indefinite backlog is not safe storage.
- No internal splitting/truncation of an AP report is allowed. Live proxy/server size limits remain to be checked under scale.

### 7.5 Backend summaries, history and acknowledgement

The backend adds `measurement_summary` to the official stored batch. Its sections include scan summaries, `ap_traffic_by_ap`, iperf3 summaries, and batch counts. Full original arrays remain alongside it.

Version-2 AP summaries currently provide:

- `peers` with their original directional/category metrics and normalized per-minute values.
- Compact `radios` with distinct count/duration sources; full histograms/distributions remain in raw data.
- `station_totals` using station `ALL` records only, and separate `backhaul_totals`.
- Compatibility `download_bytes`/`upload_bytes` from station local measured totals, not gateway-category totals.
- Legacy `frame_count` and `avg_frame_duration_us` set to null, because there is no defensible automatic equivalence.

A backend AP upload must not be acknowledged as successful until canonical temporary history storage succeeds. Failed AP history storage returns failure so NMS can retry. AP-only batches use stable content-derived measurement IDs, preventing duplicate history entries after a lost response while the indexed record remains retained. Different APs and different reports must remain separate even at identical upload timestamps.

Temporary history is not permanent DataLake. A registered experiment must still be exported and checked. Late queued reports are currently associated with upload-time experiment context; verify late-arrival attribution at boundaries before unattended use. Source measurement times, upload times and session identity must all be retained.

## 8. Proposed calculation methods for our target statistics

### 8.1 Output record and units

Target one output per interval, local AP, remote peer/link, radio/channel, direction and category, containing:

| Output | Unit / requirement |
| --- | --- |
| Interval identity | Original time bounds plus counter-group sampling windows |
| Link identity | Local AP, remote robot or AP, peer MAC, radio/interface/link ID and frequency/channel |
| Category | VO/VI/BE/BK, ALL, or BACKHAUL; ALL is a total view, not an extra traffic class to add |
| Packet count/rate | MSDUs and MSDUs/min, with provenance |
| Transmission count/rate | PPDUs or attempts and PPDUs/min; specify retries/coverage and measured/estimated status |
| Average physical-transmission duration | Microseconds per PPDU; identify exact source/population or mark proxy/unknown |
| TX exchange airtime | Microseconds over interval; separate metric from PPDU duration |
| Quality/assumptions | Reset, unknown windows, category coverage, allocated-count assumptions, population mismatch and topology confidence |

Use original intervals for validation first. For calendar-minute bins, splitting a straddling report in proportion to overlap assumes uniform traffic within the interval; mark that as estimated. A burst-edge report must not be treated as uniformly loaded without qualification.

### 8.2 Normalize counter deltas to one minute

For a count or byte delta `X` measured over its own elapsed interval `w` seconds:

$$
X_{\mathrm{per\ minute}} = X\frac{60}{w}.
$$

For byte throughput:

$$
R_{\mathrm{Mbps}} = \frac{8B}{10^6 w}.
$$

Use peer windows for local peer counters, gateway windows for gateway bytes, and firmware windows for radio counters and radio-derived allocated transmission counts. Do not scale an average duration by `60/w`; it is a duration per transmission, not a count.

Missing/nonpositive windows or reset intervals yield unknown/invalid derived values, not a guessed 60-second window. Do not subtract counter values from consecutive reports: the reports already contain deltas.

### 8.3 Fronthaul packet and category allocation

Let `N(u,d)` be measured packets for user `u`, direction `d`, and `B(u,a,d)` classified gateway bytes in category `a`.

$$
q_{u,a,d}=\frac{B_{u,a,d}}{\sum_b B_{u,b,d}},
\qquad
\widehat N_{u,a,d}=N_{u,d}q_{u,a,d}.
$$

- AP TX uses gateway **download** bytes.
- AP RX uses gateway **upload** bytes.
- These are byte-based packet-allocation estimates, not measured category packet counts.
- If category data is absent or the denominator is zero, retain measured ALL and mark the split unknown; do not assign all traffic to BK by default.
- If AP-provided category estimates are already present, retain and validate them; do not allocate them a second time.
- The assumed category proportions can cover local traffic that the gateway never saw. Preserve that limitation explicitly.

### 8.4 Physical-transmission count per peer and category

For radio `r`, direction `d`, choose a documented count `P(r,d)`:

- TX initial allocation source: `ppdus_tried_data`, including retries/broadcast traffic.
- RX initial allocation source: reported `rx.ppdus`, currently the sum of the RX MCS distribution; retry and received-traffic coverage must remain qualified.

Using all relevant peers on the radio, including backhaul:

$$
\widehat P_{u,d}=P_{r,d}\frac{N_{u,d}}{\sum_v N_{v,d}},
\qquad
\widehat P_{u,a,d}=\widehat P_{u,d}q_{u,a,d}.
$$

This assumes the same effective packets-per-transmission ratio across peers/categories. Keep fractional intermediate values; rounding may cause a small difference in sums.

Counter windows are slightly different. For more precise cross-group comparison, use normalized packet rates to form peer shares and radio transmission rates for allocated per-minute counts. When every peer has the same peer sampling window, that normalization cancels in the peer share. Do not present any such correction as a cure for unknown counter populations.

**Do not cap allocated attempts at peer packets.** Retry/broadcast populations can make attempts exceed packets. Also do not claim that this excess measures the peer's own retries.

For backhaul, apply the same peer allocation but use one `BACKHAUL` category. If a radio serves only one peer, allocation is simpler, but broadcast, management and unrelated received traffic still require scope checks. Raw radio count and allocated backhaul count remain distinct concepts.

### 8.5 Average physical-transmission duration

There are three different duration sources:

**A. Radio TX average from measured sum/count**

$$
\overline T_{r,TX,all}=\frac{S_{r,TX,all}}{P_{r,TX,all}}.
$$

Use `tx.ppdu_duration_sum_us` and `tx.ppdus_tried_total` only when coverage and validity are compatible. This average includes management/legacy attempts; it is **not automatically the average duration of data-only peer transmissions**.

**B. Radio TX/RX histogram average**

For histogram bin `i` with count `h_i`, lower edge `l_i`, and upper edge `u_i`, choose representative `m_i`:

$$
\overline T_{hist}=\frac{\sum_i h_i m_i}{\sum_i h_i},
\qquad m_i=\frac{l_i+u_i}{2}.
$$

Current firmware uses lower edge plus half bin width for the open-ended last bin. This is an assumption, not a measured tail mean. With 250-microsecond bins, all samples in the first bin produce 125 microseconds regardless of their actual within-bin mean. Empty histograms yield unknown duration, not zero.

The histogram and transmission-count populations have shown mismatches. Until resolved, do not label their product or ratio a measured physical quantity.

**C. Per-user/category duration proxy — proposed initial approximation**

No measured per-peer/category PPDU-duration distribution is available. A possible initial model is:

$$
\widehat{\overline T}_{u,a,d}=\overline T_{r,d}^{chosen}.
$$

This assigns a chosen radio-direction average to every peer/category on it. It does not reveal genuine user/category duration differences. The output must say **radio-average proxy** and record whether it uses an all-attempt mean or a histogram estimate.

**Agreement still needed:** choose the duration source appropriate to the allocated data-count population, or explicitly accept the mismatch as a rough proxy. Do not silently multiply peer data-attempt counts by an all-management-inclusive mean and call the result measured data airtime. Where no acceptable source exists, retain count statistics and mark duration unknown.

The current backend intentionally does not fabricate this per-peer duration output. We will implement the agreed calculation after reviewing this document and settling counter meanings.

### 8.6 Airtime and consistency with the performance model

A modelled physical-transmission-time contribution can be formed as:

$$
\widehat A_{u,a,d}=\widehat P_{u,a,d}\widehat{\overline T}_{u,a,d}.
$$

This is an estimate requiring compatible populations or an explicit proxy assumption. If the count is per minute, the product is microseconds per minute; divide by 60,000,000 for an estimated time fraction.

Keep measured peer TX `fes_airtime_us` separately. It includes the immediate response exchange and management traffic, unlike physical-transmission-only duration. Dividing it by packets gives exchange airtime per data packet with mismatched populations; dividing by allocated transmission counts gives an approximate exchange duration, not a measured PPDU duration.

In multi-user transmissions, one physical exchange can be attributed to several peers. Peer airtime sums can exceed actual channel time, and a physical transmission may serve multiple users. Initially interpret allocated per-user transmission counts as **equivalent shares**, not independently observed contention events. Validate single-user versus multi-user behavior before using these estimates as independent transmission arrivals.

Channel busy/TX/RX counters provide separate radio observations where available. Missing AP6 channel time must not be filled with a peer-airtime sum and called measured occupancy. Likewise, do not add a hop's TX and RX observations to double its airtime. Co-channel links can overlap/interfere; simple sums are an accounting/model input, not automatically measured network utilization.

### 8.7 Combining intervals

- Average count per minute across intervals: total count divided by total valid elapsed minutes, using the corresponding counter's windows.
- Average duration across compatible populations: total duration divided by total count, or count-weighted interval means. Do not take an unweighted mean of interval mean durations.
- Exclude/flag invalid intervals; do not fill missing reports with zero traffic.
- Retain measurement IDs to avoid counting retries twice.
- Do not average together all-transmission, data-only, histogram-only and FES durations as if they were the same quantity.

### 8.8 MCS-based duration formula is not the initial default

Measured duration sources take priority over rate-table reconstruction. MCS alone is insufficient: physical mode, bandwidth, spatial streams, guard interval, packet lengths, aggregation and overhead affect duration. Separate marginal distributions cannot reconstruct their joint distribution exactly.

If a future formula is used for comparison, record all assumptions, use a weighted duration rather than a rate obtained by simply averaging MCS values, and keep its result separate from measured sums and histogram estimates. No silent fallback PHY rate or fixed four-packets-per-transmission assumption is accepted.

## 9. Cross-check against Internet iperf3

Compare byte/rate and packet magnitudes over report windows fully inside steady traffic. Native application payload bytes differ from gateway/driver bytes because of headers and other traffic. Opposite ends can also have shifted windows and TX/RX byte definitions. Do not demand exact byte equality or automatically divide by eight.

The tests collected on November 13 establish:

| --- | --- | --- |
| Download `SEchoDn` | Receiver 4.995 Mbps; reported loss 0.133%; AP6 at both endpoints | AP6 station TX 5.260 Mbps; gateway BK download 5.228 Mbps; AP1 backhaul TX 5.304 and AP6 backhaul RX 5.340 Mbps |

These are different observation intervals and counter definitions. They support basic operation/direction/magnitude; they do not prove exact counter accuracy.

The upload receiver summary reports 95,281,200 bytes (4.225 Mbps) but the same 93,761 packets and zero loss as the sender. At 1,200 application bytes per packet, that packet count corresponds to 112,513,200 bytes. Preserve this inconsistency; do not treat zero loss as independently validated. A controlled Internet endpoint is useful later, but the public server already supports the present basic-path test.

iperf3 cannot directly validate wireless PPDU counts or durations. It supplies application traffic reference data; aggregation, wireless overhead and retransmissions are different layers.
